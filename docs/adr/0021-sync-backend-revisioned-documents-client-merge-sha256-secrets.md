# ADR 21: The sync backend — Postgres via Drizzle on Node, revisioned documents merged on the device, SHA-256 device secrets

**Status:** Accepted
**Date:** 2026-09-24
**Supersedes:** Nothing. It refines `architecture.md` §9.2–§9.4 and §10, which are amended in place with dated notes pointing here. ADR 4 (sync on by default, no sign-in) and ADR 5 (pairing by code, no auth library) stand unchanged. This is how they are built.

## Context

Slice 2 builds multi-device sync. The architecture sketched it:
- a Postgres replica of progress records (§9.2);
- an anonymous device secret stored as an **Argon2id** hash (§9.3);
- last-write-wins on `updatedAt`, with a timestamp watermark (§9.4);
- three routes on the Edge runtime (§10).

Building it surfaced four problems with that sketch:

1. **No progress record carries `updatedAt`.** `ScheduleEntry`, `Session` and settings never had one. Gate B (human, 24 September 2026) decided that the lower Leitner box wins a concurrent edit (`progress.md` D43, D69). But a plain `min(box)` stops a box from ever rising once it has synced, so the service has to tell *concurrent* edits from *causally later* ones.
2. **A timestamp watermark is unsafe across devices.** Clock skew can hide a write, and two pushes committing out of order can leave a gap.
3. **Argon2id fits the wrong threat.** A slow, salted hash makes guessing a low-entropy password expensive. The device secret is 256 random bits, so there is nothing to guess. Argon2id would still need a native dependency, cost tens of milliseconds and a large block of memory on every sync request, and, being salted, force the device id to travel with every request so the hash could be found.
4. **The Edge runtime is deprecated in Next.js 16** (`node_modules/next/dist/docs/…/runtime.md`), and a TCP Postgres driver with transactions needs Node anyway.

## Decision

- **Stack.** Postgres through Drizzle (`drizzle-orm`), driven in production by postgres.js (`postgres`). It is provider-neutral: Neon or any Postgres over `DATABASE_URL`, with `prepare: false` for serverless poolers. Tests and the hermetic E2E lane use Drizzle's PGlite driver over the `@electric-sql/pglite` the repository already uses. Migrations are SQL generated by `drizzle-kit` from `apps/web/src/server/schema.ts` into `apps/web/drizzle/`, and committed. **Every route runs on Node**, which is Next 16's default.
- **Location.** The server lives in `apps/web/src/server/`:
  - the schema, a `SyncRepository` whose every method is keyed by account, and its Drizzle implementation;
  - pure `Request → Response` handlers;
  - one server-side composition point, `db.ts`.

  The route files under `src/app/api/` are one-line bindings. There is no new package; ADR 11 already says that self-hosting means reworking only `apps/web`. A dependency-cruiser ban keeps `drizzle-orm`, `drizzle-kit` and `postgres` inside `apps/web/src/server/`.
- **Revisioned documents, merged on the device.**
  - Each account keeps a revision counter. Every accepted write takes the next value, under a row lock, so two concurrent pushes never interleave.
  - A document's revision is the pull watermark, and pulls page by it.
  - A push names each document's `baseRevision`. The server takes the write only while that revision is still current; otherwise it returns its own copy as a conflict.
  - The **device** merges with one pure rule, `mergeRecord` in `@palier/app`, and pushes again. So payloads stay opaque to the server, as §9.2 wants, and the Gate B rule exists in exactly one place.
  - A device finds its dirty records by comparing a hash of each record against a local ledger, kept behind the new `SyncStateStore` port.
- **Device secrets are stored as SHA-256**, unsalted and uniquely indexed, so the bearer alone finds its device. The server never generates a secret. A joining device presents the one already in its vault.
- **Pairing codes** are six characters from an alphabet without 0/O/1/I/L, drawn by rejection sampling so each character is equally likely. They are stored hashed, valid for ten minutes, and redeemed by one conditional `UPDATE … RETURNING`, so two devices cannot both win the same code.
- **Rate limiting uses a Postgres table, not a library.** The key is an HMAC of the route, the IP and the UTC day under a server secret (`RATE_LIMIT_SALT`), so no IP and no stable pseudonym for one is ever stored (§12). The limits:
  - registering: 20 an hour;
  - issuing codes: 20 an hour;
  - redeeming: 10 in ten minutes, against roughly 887 million codes.
- **With no database configured, every route answers 503.** The client shows that as a quiet "not syncing" (§11).

## Consequences

- A box rises after it syncs, and a genuine disagreement between devices falls to the lower box on both, which is what Gate B asked for.
- Sync performs a full enumeration of each local store on every run, the `all()` that D61 added. At the §9.4 capacity model's heavy user (about 20,000 attempts a year), that is a few megabytes of hashing per sync, which is acceptable at the §9.4 trigger rate.
- Tombstones (§9.4) are deferred, because nothing deletes a single record yet. The `deleted` column exists and nothing sets it.
- The 90-day tombstone purge and the 180-day inactive-account deletion are not built. They are Slice 3's or Phase 7's scheduled jobs.
- New dependencies, none replacing anything:
  - `drizzle-orm` and `postgres`, which the §3 stack table already names;
  - `drizzle-kit`, a development dependency that generates the migrations;
  - `zod` in `apps/web`, the version `@palier/domain` already pins, for request validation;
  - `@electric-sql/pglite` becomes a direct dependency of `apps/web` for the hermetic server path.

## Alternatives considered

- **Add `updatedAt` and last-write-wins (Gate B option 1).** Rejected by the human decision. It regresses a box whenever the later write came from the device that saw less.
- **Merge on the server.** This would make payloads non-opaque and put a second copy of the merge rule in the server. Rejected.
- **An outbox of changed records.** Every store's write path would have to know about sync, and an import or a merge would need extra care. The ledger diff covers all three for free. Rejected.
- **Argon2id, as §9.3 wrote it.** Rejected by human decision, for the cost and threat-model reasons in Context.
- **A separate server package.** No arrow in §3.1 calls for one, and ADR 11 places server rework in `apps/web`. Rejected.

## Revisit when

- A full-store enumeration per sync shows up in the §13 performance budget. Then replace the ledger diff with an outbox or per-store change counters.
- The provider needs a driver postgres.js cannot serve, such as HTTP-only serverless at the edge.
- A record type gains a genuine per-record deletion, which needs tombstones.
